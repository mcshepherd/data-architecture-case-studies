Data Architecture Case Studies · No. 1

Detecting Inserts, Updates, and Deletes Without TombstonesHash-Diff Synchronization over a Linked Server

How a nightly replica of a vendor ERP stays exact under a hard query timeout, a query-text limit, and no tombstones: the method, shown in the SQL it generates.

Colby Shepherd

I designed and built a nightly sync that kept a warehouse copy of a vendor ERP exact: roughly 700 tables and 2 billion rows, reconciled every night in about 38 minutes, replacing a process that took about 9 hours. The client's code stays with the client, so I rebuilt the method from scratch against a generated stand-in ERP, in the same T-SQL, over a real SQL Server linked server. The generated statements below are real output from that rebuild; the few code excerpts are marked where abridged.

The constraints decide the design

The ERP was reachable only through a linked server backed by the vendor's proprietary driver. Six facts shaped everything that follows:

  • A 15-minute hard timeout on any query that has not yet returned a row. A plain SELECT * streams and can run for hours; a query that computes must finish inside it.
  • A limit on query-text length, which caps how much any one statement can say.
  • Read-only access. No staging tables, temp tables, or views on the vendor's side.
  • No tombstones. A deleted row simply disappears.
  • Create and modify dates that cannot be trusted: sometimes missing, sometimes not updated when a row changes.
  • Undeclared keys. The real keys are composite, an int plus codes and sometimes a date, and live only in the vendor's data dictionary.

Untrustworthy dates rule out filtering for recent changes, and missing tombstones rule out asking for deletes. What remains is comparing every row, every night, and making that cheap.

One path for every table

One procedure runs once per table, many tables in parallel. The first load, a nightly run, and a full rebuild all take the same eight steps (a rebuild skips the guard and treats every key as new), and every statement sent to the ERP is generated from two things: a copy of the ERP's column metadata, and a hand-kept manifest of each table's key columns.

Three staging tables per table

Every step reads or writes three tables in a stage schema on the warehouse, created fresh at the start of each table's run and named for the table they serve. They are ordinary tables, not #temp tables, so a table that fails leaves its last attempt's staging in place to inspect. Because the names belong to the table rather than the run, two syncs of the same table would collide, so each table's run holds an application lock.

1Pull every key and a hash of its whole row

One query per table returns each key and an MD5 of the entire row, computed on the ERP's side, so only keys and 32-character hashes cross the wire. In production this single pull finished inside the timeout even at 500 million rows. For a thirteen-column table it looks like this, reformatted from the one line actually sent:

Every detail in that statement is there to make the hash honest:

  • Each type gets its own cast, in a style that keeps full precision: 2 for money, 3 for float, 121 for datetime, 23 for date. The defaults round money to two decimals, cut float to six significant digits, and drop datetime's seconds.
  • NULL becomes CHAR(0), a character real text values do not contain, so NULL and an empty string hash differently.
  • The delimiter is $|$, so a pipe moving from one value to its neighbor cannot produce the same string.
  • Every CONCAT starts from @m, a varchar(max). Without it, SQL Server silently truncates at 8,000 characters, or 4,000 once an nvarchar column joins in. I hit this in production; the rebuild hit it again independently. CONCAT takes at most 254 arguments, so wide tables nest one per 126 columns.

Each row below is a one-row change made in the stand-in ERP. An obvious first-draft hash (default conversions, NULL as an empty string, a single pipe, no varchar(max)) misses every one; the sync catches them all.

The ERP's hash is stored on each replica row, and the next night compares against it. The warehouse never reproduces the ERP's casting, so the two sides never hash the same row differently. MD5 is enough here: it detects change rather than tampering, and the odds of two versions of a row colliding are negligible.

2–4Guard, compare, prune

A short pull looks exactly like mass deletion, so before comparing anything the procedure checks the count. The replica may shrink by deletes, but only so far. @wipe marks a full rebuild, and @allowance is each table's permitted shrink, 1 percent by default:

Then one pass over the pulled hashes classifies every key. A key the replica lacks is new; a key whose hash differs, or that was deleted and has come back, is changed; a key active in the replica but absent from the pull was deleted in the ERP. Unchanged keys are dropped, and what remains is the request list.

5Send the keys back inside the query text

Nothing can be created on the ERP, so there is nowhere to put a list of keys except the statement itself. Each requested key becomes a literal tuple in a VALUES list, joined on every key column, and each batch's rows land in __rows through INSERT … EXEC over the linked server:

The batch size is arithmetic on the statement. The select list, the FROM, and the join are the same for every batch of a table: 387 characters here. The rest of the 32,767-character limit, 32,380 characters, is room for keys. These keys average 18.8 characters with their commas, so the first batch carries 1,723 of them and ends 22 characters short of the limit; the last batch carries the remaining 1,038.

6–7Apply everything at once, then prove the counts

Fetched rows land in staging. Nothing touches the replica until every batch is in; then one transaction flags the deletes, removes the changed rows, and inserts the fetched ones, each stamped with its load time and the hash from the pull. Each statement captures its own row count, and before the transaction commits, step 7 checks each one against what the earlier steps said to expect: rows flagged against keys found deleted, rows removed against keys found changed, rows inserted against keys requested, and the replica's active rows against keys pulled. Any mismatch rolls the whole table back:

That makes failure cheap. Attempts are nested, up to three per fetch batch inside the procedure and three per table in the runner, and a failed INSERT … EXEC inserts nothing, so a retry never duplicates a row. A table that fails every attempt is left exactly as it was the night before, and the next run picks up everything it missed. 8Log every count, then clean up

Every attempt at a table writes one log row: when it started and finished, how many keys it pulled, how many were new, changed, and deleted, how many rows it requested, fetched, and wrote, how many batches it sent and retried, and the longest statement it sent to the ERP. A table that fails records how far it got, from its pull, compare, and fetch counts, and the error that stopped it. The alert email above is built from this log.

Staging is dropped only after the log records success. A failed table keeps the staging from its last attempt for inspection until its next run starts fresh. Once the changes are committed, an error in logging or cleanup is recorded against the run but does not mark the table failed, because its replica is already right; only a missing log row, which leaves nothing to record against, raises the error.

Proving it without the client's system

The stand-in is generated in T-SQL from a seed: 120 tables and 1.2 million rows with undeclared composite keys, quoted codes, untrustworthy dates, and tables up to 318 columns, plus nightly activity that inserts, updates, deletes without a trace, and re-creates deleted keys. The read-only login is real. The timeout is real but scaled down with the data, to 30 seconds from 15 minutes, and a wrapper turns it into an error as the vendor's driver did. The text limit is the one constraint simulated, at 32,767 characters, in the single procedure every ERP call passes through.

To check the rebuild, an independent audit compares every row of every table with the ERP after each run. It is test scaffolding, not part of the sync: it reads the ERP through its own linked server and fingerprints rows with SQL Server's JSON rendering and SHA-256, so a bug in the sync's hashing cannot hide from it. The old process ran beside the new one on the same nights, rebuilt as it was: most tables reloaded in full, the large ones filtered by date and upserted, most on only part of their key.

What I would do differently

  • Close the gap between the pull and the fetch. The stored hash comes from the pull and the values from the fetch. A row that changes in between, then changes back before the next pull, keeps the in-between values. I never saw transactions land at that hour, but it is possible; fetching each row's hash with its values would close it.
  • Retry only what a retry can fix. Every failure except the variance guard is retried, including errors that can never succeed on retry, such as schema drift or a statement over the text limit.
  • Handle schema changes in place. A vendor change to a table's columns stops that table, by name, until it is rebuilt from scratch. Adding the column and refetching that one table would keep it running.
