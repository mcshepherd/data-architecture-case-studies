Two SQL Server 2022 instances: `erp` (the stand-in vendor ERP) and `warehouse`. The warehouse reaches the ERP only through the linked server `ERP`, as `erp_reader`, a login with read-only access. The linked server's query timeout is 30s, standing in for the vendor driver's 15-minute hard timeout at reduced scale.

## Queries are killed at the timeout

Expected: cancelled at 30s, although the query would finish at 40s. Note the exit code: the provider reports the timeout as an informational message, not an error.

```sql
EXEC ('WAITFOR DELAY ''00:00:40''; SELECT 1 AS finished') AT ERP
```

Exit code 0 after 31s:

```
OLE DB provider "MSOLEDBSQL" for linked server "ERP" returned message "Query timeout expired".
```

## Timeouts are silent inside a procedure

Expected: the same timeout inside TRY/CATCH raises no error and pulls zero rows. A pull that times out looks exactly like a table with no rows. Any step that trusts an empty result would treat every local row as deleted, so the process must check row counts rather than rely on errors.

```sql
-- A timed-out linked-server query inside TRY/CATCH, the way a procedure would run it.
SET NOCOUNT ON;
CREATE TABLE #pulled (n int);
BEGIN TRY
    INSERT INTO #pulled EXEC ('WAITFOR DELAY ''00:00:40''; SELECT 1') AT ERP;
    SELECT 'no error raised' AS outcome, @@ERROR AS error_number, (SELECT count(*) FROM #pulled) AS rows_pulled;
END TRY
BEGIN CATCH
    SELECT 'error caught' AS outcome, ERROR_NUMBER() AS error_number, (SELECT count(*) FROM #pulled) AS rows_pulled;
END CATCH
```

```
OLE DB provider "MSOLEDBSQL" for linked server "ERP" returned message "Query timeout expired".
outcome error_number rows_pulled
------- ------------ -----------
no error raised 0 0
```
